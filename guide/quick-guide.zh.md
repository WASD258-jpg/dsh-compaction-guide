# 快速指南 —— 会话变慢、损坏或垂死时该怎么办

> 属于 [dsh-compaction-guide](../README.md) 的一部分。引用 `[S…]`/`[O…]`/`[P…]`
> 解析于 [`../REFERENCES.md`](../REFERENCES.md)。

本页回答一个问题：**我的会话表现异常 —— 我该做什么？**

这里没有任何内容要求你信任某个主张；每条建议都链接到它背后的测量。凡是修复有代价的，
代价都已写明。

---

## 1. 先弄清实际发生了什么

不要猜。「我的会话坏了」这个症状在 DSH 中至少有四种不同成因，它们需要不同的应对。

对自己的日志运行诊断：

```sh
node tools/doctor.mjs "$DSH_HOME/sessions"
```

它会报告压缩成功率、失败分类、HTTP 状态码 → 所赋错误码的映射，以及是否发生过重试风暴。
`--json` 供机器读取，`--merge` 用于统计重叠快照而非去重 [O3]。

**输出告诉你什么：**

| 读数 | 可能原因 | 去看 |
|---|---|---|
| 成功率远低于 100% | 摘要请求超出预算 | [§2](#2-压缩了但失败的会话) |
| 任意 `413 → INVALID_REQUEST` | 溢出恢复不可达 | [§3](#3-永不恢复的溢出) |
| 连续失败且间隔不变 | 没有退避 | [§4](#4-重试风暴) |
| `compaction/start` 没有对应的 `compaction/end` | 压缩中途崩溃 | [§5](#5-孤立的压缩) |
| 什么都没有 | 你的会话从未压缩 —— 去别处找 | [§6](#6-当问题不在压缩时) |

---

## 2. 压缩了但失败的会话

**症状。** 压缩运行、失败、再次运行。会话最终停止推进。在这里分析的语料中，
成功率为 **17.6%** [O4]，且**约 95% 的失败携带同一条错误文本** [O5]。

**原因。** 摘要请求逐字重放被压缩区且没有大小守卫 [S6]，而溢出路径同时通过传入零保留预算
把该区域放到最大 [S5][S9]。摘要模型默认使用**当前正在使用的路由** [S7]。当该路由的窗口
小于被压缩的历史时，摘要请求放不下。

**对照证据。** 同一台机器、同一套插件栈，唯一变量是窗口大小 [O8]：

| 摘要路由窗口 | 压缩次数 | 成功 |
|---|---|---|
| 1,000,000 | 7 | **7** |
| 262,144 | 22 | 1 |

**该做什么。** 固定一条独立的大窗口摘要路由。这是不改代码就能做到的最高影响改变。
完整说明，包括这个设置**位于何处**（一个常见陷阱 —— 它不在你的 profile patch 层
[O17][O18]）：

→ [`../config/README.md`](../config/README.md)

**代价。** 更低的 `thresholdRatio` 会让压缩**提前 26%** 触发，这意味着
**更多按真实 token 计费的摘要调用** [O22]。如果你不愿付这个代价，只固定摘要路由，
把阈值留在默认值。

**残余风险。** 拼错的摘要提供方或模型会**静默通过启动**，只在压缩首次运行时才失败
—— 可能是数小时之后 [O22a]。在依赖它之前，先对照你的 provider 块核对这些名称。

## 3. 永不恢复的溢出

**症状。** 会话撞上硬墙。每个回合都失败；上下文从不缩小；你做什么都没用。

**原因。** 响应体不含提供方消息的 HTTP 413 被归类为 `INVALID_REQUEST` [S1][S2][S3]，
而恢复钩子要求 `CONTEXT_WINDOW_EXCEEDED` [S4]。**观测到的 239 次 413 中，100% 被误判**
[O6]。一个会话内对照确认了该机制：状态码 **400** 触发压缩 2 次且**两次都成功**；
状态码 **413** 触发压缩 **零次** [O10]。

**关于「已交接」状态的说明。** 如果你的 UI 显示交接，那**不是**压缩失败 ——
被交接的会话在那一刻压缩次数为零 [O12]。链条是：请求失败 → 压缩从未运行 → 卡死 →
*你*运行 `/rescue` → 交接。

**该做什么。** 安装一个恢复该分类的插件：

```yaml
- insert:
    - id: length-stop-overflow
      name: '@argszero/cordis-plugin-length-stop-overflow'
```

**验证。** 该插件尽管声明了更窄的 peer 范围，**已针对真实的 `0.2.0-rc.2` 宿主测试过**：
它能安装、加载，并重新分类此处记录的确切失败形态 [O15]。

**风险。** 任何 `status === 413` 都会在其措辞被查看之前被重写 [O16]，
因此无关的 413 —— 比如图片尺寸拒绝 —— 也会被重新分类。影响是有界的：浪费一次压缩，
原始错误仍然保留。先用 `mode: 'warn'` 观察你自己流量上的比率。

→ [`../PRIOR-ART.md`](../PRIOR-ART.md) 了解该插件的完整适用范围及其不兼容性。

## 4. 重试风暴

**症状。** 日志被反复的压缩尝试填满。会话感觉卡住。语料中测得：
**单个回合内 18 次连续失败**，间隔最小 76.6 s / 中位数 101.2 s / 最大 778.1 s ——
**间隔不随失败次数增长** [O11]。

**原因。** 失败处理器只记录日志然后继续 [S11]。`pressure` 路径没有会话级计数器 [S14]。

**该做什么 —— 并且把局限说清楚。** **没有任何插件能阻止这一点**。熔断器行为需要在尝试
*发生之前*就跳过它，而 `compaction-basic` 是在**它自己的 `agent/pre-step` 监听器体内**
执行该调用 [O24] —— 在其 `next()` 之前 —— 因此没有任何 waterfall 顺序能拦截它。
修复需要上游监听器内部的一个守卫。

**今天你能做的：**

1. **减少触发次数**，于是失败的机会更少 —— 见 [§7](#7-主动裁剪)。
2. **让失败可见。** 今天每次失败都只是一句光秃秃的 `logger.warn` [S11]；
   没有任何东西告诉你压缩正在剧烈抖动。
3. **更早地把卡死的会话当作不可恢复**，而不是等过几十次重试。

这个否定结果被完整公布，因为仅读任何一个扩展点都看不出这种布局：
[`../verify-feasibility/`](../verify-feasibility/)。

## 5. 孤立的压缩

**症状。** 一个 `compaction/start` 没有匹配的 `compaction/end`。

**原因。** 该设计在摘要产出之前追加 `compaction/start`，并用 `compaction/end` 释放；
两者之间的崩溃会刻意留下一个可检测的孤儿。

**好消息。** 在分析的语料中，**84 次 start 与 84 次 end 100% 配对** ——
零孤立 start，也没有任何压缩区间跨越 `session/end-seed` [O25]。
这是设计时考虑到的状态，不是常被观测到的状态。

**该做什么。** 如果诊断报告了未匹配的 start，说明会话在压缩中途被中断。
恢复会话通常就够了；一旦进程生命周期推进，该孤儿就会被识别为陈旧。

## 6. 当问题不在压缩时

一次报告**零次压缩**的诊断运行意味着你的会话从未达到阈值 ——
因此无论哪里出了问题，都不是压缩。

**一个值得知道的陷阱。** 在日志中搜索文本 `CONTEXT_WINDOW_EXCEEDED` 会产生假阳性：
一个仅仅*讨论过*该常量的会话贡献了 66 次文本命中，而**真实错误事件为零** [O13]。
这就是诊断按结构化事件类型与载荷字段计数、而不是按子串计数的原因。

## 7. 主动裁剪

**适用于**你想减少压缩触发频率的场景。

工具结果裁剪器可以被独立调用 —— 已验证：第三方插件可以取得该服务并成功调用
`pruneSession()` [O26]。

**以独立包 `dsh-compaction-prune` 发布 —— 但先读它的局限。**
它是一个刻意的部分措施，它自己的 README 也是这么说的。它尚未发布到任何 registry 上；
在发布之前请从源码构建。

```sh
npm install dsh-compaction-prune
```

```yaml
- insert:
    - id: compaction-prune
      name: 'dsh-compaction-prune'
      config:
        mode: warn      # observe first; it mutates durable session state
```

**它做什么。** 在上下文达到压缩阈值*之前*裁掉过大的工具输出，于是压缩被触发的次数更少。

**它不做什么。** 它**不**增加退避。如果压缩确实失败了，重试仍然不受限制
[§4](#4-重试风暴)。把它当作减少失败的*机会数量*，而不是让失败变安全。

**未做端到端验证。** 每一步都被孤立测试过，但没有任何测量证明在长会话上启用它真的会减少
压缩尝试次数。如果你试了，那个前后对比就是值得报告的数字。

> **这不是垂死会话的解法。** 如果你的会话完全停止推进，重要的是 §3。

## 8. 在几种修复之间选择

| 如果你的优先事项是… | 这样做 | 不要这样 |
|---|---|---|
| 完全阻止会话死亡 | §3（分类）+ §2（摘要路由） | 只用 §7 —— 它只是推迟 |
| 压低成本 | 只用 §2 的摘要路由 | 降低 `thresholdRatio` —— 调用次数更多 |
| 弄清发生了什么 | §1 诊断 | 从 UI 上猜 |
| 修复重试风暴 | 目前无解 —— 向上游报告 | 任何插件 —— 都不行 [O24] |

**不要组合两个压缩后端。** 五个插件替换同一个服务，并且**一起启动会失败**；
见 [`../PRIOR-ART.md` §2](../PRIOR-ART.md)。

## 9. 向上游报告什么

两个相关讨论都开着。如果诊断在这里发现了什么，附上你的数字会有帮助：

| 发现 | 位置 |
|---|---|
| 413 被归类为 `INVALID_REQUEST`，无恢复 | [#7626](https://github.com/deepseek-ai/deepseek-harness/discussions/7626) [S16] |
| 输出计数可忽略的长度停止 | [#7214](https://github.com/deepseek-ai/deepseek-harness/discussions/7214) [S15] |
| 没有退避的重试风暴 | 尚未提交 —— 守卫属于 `compaction-basic` 的 pre-step 监听器 [O24] |

附上你的诊断输出（`--json`）以及你正在运行的上游修订版。本指南中的计数来自一个语料 [O1]，
并且明确**不可推广** [EVIDENCE §8.1](../EVIDENCE.md) —— 你的可能不同，而那种不同本身就有价值。
