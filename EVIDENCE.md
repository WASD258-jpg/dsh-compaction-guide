## 2. Corpus-level counts

> **Read this before quoting any number below.** A session directory keeps
> **overlapping snapshots of the same session** — `session.jsonl.zstd`,
> `session.v3.jsonl.zstd`, `session.v4.jsonl.zstd` — which are cumulative views,
> not disjoint segments. Counting every file inflates every total. Both counts
> are reported; the de-duplicated one is the honest rate.

| Event type | Per-session (de-duplicated) | All snapshots (union) |
|---|---|---|
| `compaction/start` | **51** | 84 |
| `compaction/end` | **51** | 84 |
| **`compaction/summary`** (succeeded) | **9** | **21** |
| `compaction/prune` | — | 129 |
| **Failed closures** (`compaction/end` carrying `error`) | **42** | **63** |

**Success rate 9/51 = 17.6%** de-duplicated, or 21/84 = 25.0% across all
snapshots. In both cases the arithmetic closes exactly — every `start` either
produced a `summary` or closed with an error.

The inflation is visible directly: the union run lists `session-5f8b1111` once per
stored snapshot, each with an identical `starts = 22`. The de-duplicated run
lists it once. Per-session totals for the three sessions that ever compacted sum
to `22 + 22 + 7 = 51`, matching the de-duplicated `start` count exactly.

> **Picking the snapshot is a real trade-off, not a detail.** The snapshots are
> not nested: a later snapshot may compact events away, so its total event count
> can *fall* while its newest timestamp *rises*. Selecting by event count alone
> silently dropped recent evidence in testing — a directory reported 5
> compactions instead of 7, and 413 failures disappeared entirely.
> `tools/doctor.mjs` scores by **recency first, volume second**; `--merge` gives
> union semantics instead.

### 2.1 Error text distribution

`compaction/end` persists `error` as a **flattened string** produced by
`errorChain()`. The `code`, `name`, and `cause` fields are **not persisted** —
so an "error code distribution" is physically unavailable at this layer and
counts must be taken by rendered text.

| Count (de-dup / union) | Error text |
|---|---|
| **40 / 60** | `pi-ai detected context overflow for model "<model>"` |
| 2 / 3 | `DeepSeek request aborted by caller` |

**Overflow accounts for 95% of all compaction failures.** This is a structural
defect, not intermittent flakiness.

### 2.2 HTTP status distribution

| Status | Code assigned | De-dup | Union |
|---|---|---|---|
| 413 | `INVALID_REQUEST` | **239** | 478 |
| 400 | `CONTEXT_WINDOW_EXCEEDED` | 9 | 14 |

**Every 413 — 100% — was classified `INVALID_REQUEST`, with zero exceptions.**
Every sample carried the identical fallback text
`DeepSeek Messages request failed (413)`; **not one carried a provider-authored
`error.message`**.

### 2.3 A false positive worth recording

An early pass counted **248 "overflow hits"** by full-text searching for
`CONTEXT_WINDOW_EXCEEDED` [O13]. That number is **wrong**. One session that merely
*discussed* the constant (reading `error.d.ts`, reasoning about it, quoting it in
a prompt) contributed 66 hits with **zero real error events**.

> **Methodology rule**: never count by substring across a whole event. Count by
> **structured event type plus payload field**. Full-text matching cannot
> distinguish "an error occurred" from "an error was mentioned".

The same hazard applies to the snapshot question in §2: the union totals [O4b]
are reproducible, but they answer a different question than the de-duplicated
totals [O4]. Both are reported so neither can be mistaken for the other.

## 3. Root cause A — 413 misclassification

### 3.1 The code path

`packages/llm/llm-deepseek/src/transport.ts:31-33`

```ts
else if (isContextWindowExceededError(detail)) code = 'CONTEXT_WINDOW_EXCEEDED'
else if (status === 400 || status === 413 || type === 'invalid_request_error') code = 'INVALID_REQUEST'
```

The **order is correct** — the text classifier is consulted before the status
code. The defect is upstream of it: when the response body carries no
`error.message`, the adapter synthesizes a fallback at `transport.ts` that reads

```
DeepSeek Messages request failed (413)
```

which contains no `context` keyword. All three regexes in
`isContextWindowExceededError` (`packages/llm/llm/src/error.ts:58`) miss, and the
error falls through to the `status === 413` branch.

The recovery hook is gated on exactly that code —
`packages/compaction/compaction-basic/src/index.ts:180`:

```ts
if (failure.code !== CONTEXT_WINDOW_EXCEEDED_CODE) return next()
```

**The adapter's own fallback string defeats the classifier it feeds.**

### 3.2 Consequence chain

```
provider returns 413 with an empty body
  → adapter synthesizes "DeepSeek Messages request failed (413)"   (no context keyword)
  → isContextWindowExceededError misses on all three regexes
  → status === 413  →  INVALID_REQUEST
  → compaction-basic:180 gate does not match  →  return next()
  → overflow recovery never runs
  → context is never reclaimed
  → session stalls
  → user runs /rescue  →  UI shows "已交接"
```

### 3.3 Controlled comparison — same session, same model, same window

The cleanest available evidence. Within a single session, both statuses occurred:

| Status | Classified as | Triggered compaction? | Outcome |
|---|---|---|---|
| **400** | `CONTEXT_WINDOW_EXCEEDED` | **3 times**, within **+9 ms / +25 ms / +32 ms** | **all succeeded** |
| **413** | `INVALID_REQUEST` | **never** | failed |

**Same session, same model, same declared window. The only variable is the HTTP
status code.** This rules out "the compaction logic itself is broken" — the logic
works whenever it is reached.

### 3.4 Causal direction of "已交接"

The handoff is **not** a consequence of compaction failing. The session that was
handed off had `failedEnds = 0` and **zero compactions at the moment of handoff**.
The chain is: request fails → compaction never triggers → session stalls → the
**user** runs `/rescue` → handoff. Timestamps confirm it: `session/title` and
`handoffs.jsonl.at` share the identical millisecond `1789659712327`, and the
originating event's `source.kind` is `"user"`.

## 4. Root cause B — the summarization request is unbounded

### 4.1 Three interacting lines

`summarizer.ts:145-155` — one request carrying the whole region, verbatim:

```ts
const messages: RequestMessage[] = [
  ...input.messages,
  deepFreeze({ role: 'user', content: [{ type: 'text', text: COMPACTION_INSTRUCTION }] }),
]
```

`index.ts:299` — the overflow path passes `retainTokens = 0`:

```ts
const range = selectCompactableRange(agent.session, measurement, 0)
```

With `retainTokens = 0`, `selectCompactableRange` (`region.ts`) breaks out of its
accumulation loop on the first iteration (`accumulated >= 0` is immediately
true), so `keepFromIdx` lands at `length − 1` — **the retained tail is a single
node and the compacted region expands to nearly the entire surface.**

`summarizer.ts:137` — the summarization target falls back to the live route:

```ts
const target = configured ?? latest ?? agentTarget
```

`configured` is the (empty by default) `summarizationProvider`/`summarizationModel`
pair; `latest` is **the conversation's currently routed model**.

**The result: the entire region is sent with no size guard, on whatever route the
conversation currently uses.** Whether that request fits is not decided by the
summarizer — it is decided by the window of the route the conversation happens to
be on at that moment.

### 4.2 Controlled comparison — the only variable is the conversation's route

An earlier version of this section presented the comparison as "window size",
with `5f8b1111` labelled as running its summarizer on `stealth/ox-alpha`. **That
was a misreading of the data, and it is corrected here.**

The measured `compaction/summary` payload records the summariser's own `provider`
and `model`. In `5f8b1111` the summary ran on `deepseek-official/deepseek-v4-flash`
— a **1,000,000**-token route — and **succeeded**. What changed over the session
was the **conversation's route**, and the failures track that exactly:

| Route in force (declared `contextWindow`) | Compactions | Succeeded | Failed |
|---|---|---|---|
| `deepseek-official/deepseek-v4-flash` (**1,000,000**) | 1 | **1** | 0 |
| `openrouter/stealth/ox-alpha` (**262,144**) | 18 | 0 | **18** |
| back to `deepseek-v4-flash` (**1,000,000**) | — | — | none |

Every failure carries the name of the model it failed on:

```
pi-ai detected context overflow for model "stealth/ox-alpha"
```

Cross-session the same pattern holds: `c0acb35e` ran on a 1,000,000-token route
and compacted **7/7**.

**Physical evidence, read correctly.** The one success in the failing session had
`shadowedTokenCount` = **557,896** and `inputTokens` = **791,091**. Because the
payload also records `provider: deepseek-official` and `model: deepseek-v4-flash`,
that request went to a **1,000,000**-token window — so it did not overflow, and
describing it as "557K tokens pushed into a 262K window" was wrong.

The defect this section documents is real, but it is **the absence of a guard**,
not an undersized window: the same 791,091-token request on a 262,144-token route
would fail, and nothing in the summarizer would prevent it.

### 4.3 Why the summarization failure cannot self-heal

`summarizer.ts:162` sends the request through a **direct** `ctx.llm.stream()`
call — it does **not** pass through the agent loop. The only overflow-recovery
entry point is the `agent/request-error` waterfall, dispatched by the loop
(`packages/core/agent-loop/src/...`). A direct call therefore **never dispatches
`agent/request-error`**, so its overflow can never reach recovery.

The secondary hook, `compaction/summary-error`, has exactly one listener in the
shipped composition — `compaction-image-offload` — which only handles
`IMAGE_OFFLOAD_REQUIRED_CODE` and returns `false` for anything else.

**Net effect: a summarization overflow has no recovery path at all.**

## 5. Root cause C — no backoff, no circuit breaker, no visibility

`index.ts` (the `agent/pre-step` listener) catches every failure and logs it:

```ts
catch (error) {
  const message = error instanceof Error ? error.message : String(error)
  ctx.logger.warn(`step compaction failed: ${message}; continuing the turn`)
}
```

The turn continues, the context is still full, and the next step triggers
compaction again. `maxOverflowRetries` (default 1) is counted **only** on the
`agent/request-error` path; the `pressure` path has **no global retry counter**.

### 5.1 Measured retry intervals

From the worst session (22 starts):

| Metric | Value |
|---|---|
| Consecutive failures in one turn | **18** |
| Minimum interval | 76,631 ms |
| Median interval | 101,173 ms |
| Maximum interval | 778,069 ms |
| Total failure span | 5,391 s (**89.9 minutes**) |

**The interval does not grow with the failure count.** A backoff would show
increasing gaps; this shows a flat distribution — retries are unconditional.

## 7. Reproduction

### 7.1 Decode a session log frame-by-frame

```js
import fs from 'node:fs'
import zlib from 'node:zlib'

const MAGIC = [0x28, 0xb5, 0x2f, 0xfd]

function decode(file) {
  const buf = fs.readFileSync(file)
  const offsets = []
  for (let i = 0; i + 4 <= buf.length; i += 1) {
    if (buf[i] === MAGIC[0] && buf[i + 1] === MAGIC[1]
      && buf[i + 2] === MAGIC[2] && buf[i + 3] === MAGIC[3]) offsets.push(i)
  }
  const parts = []
  for (let i = 0; i < offsets.length; i += 1) {
    const slice = buf.subarray(offsets[i], i + 1 < offsets.length ? offsets[i + 1] : buf.length)
    try { parts.push(zlib.zstdDecompressSync(slice)) } catch { /* incomplete tail frame */ }
  }
  return Buffer.concat(parts).toString('utf8')
}

const events = decode(process.argv[2]).split('\n')
  .filter(Boolean)
  .flatMap(line => { try { return [JSON.parse(line)] } catch { return [] } })

const counts = {}
for (const e of events) counts[e.type] = (counts[e.type] ?? 0) + 1
console.log(counts)
```

### 7.2 Count failures by structured payload, not by substring

```js
const ends = events.filter(e => e.type === 'compaction/end')
const failed = ends.filter(e => e.data?.error !== undefined)
const byText = {}
for (const e of failed) byText[e.data.error] = (byText[e.data.error] ?? 0) + 1
console.table(byText)
```

### 7.3 Reproduce the classification defect without a live provider

## 8. Threats to validity

Stated explicitly, because the recommendations in [PLAN.md](PLAN.md) rest on them.

**8.1 Single-corpus scope.** All counts derive from one user's session logs [O1].
The *frequencies* — 17.6% success, 239/239 misclassified, 18 consecutive failures
— describe that corpus and **do not generalise** to other installations. The
*mechanisms* are established against pinned upstream source [S1]–[S14] and are
not corpus-specific. Where a claim depends on frequency, it is stated as an
observation about this corpus, not as a rate.

**8.2 Persistence-layer limitation.** `compaction/end` omits error codes [O14],
so the failure taxonomy [O5] is by rendered text rather than by code. Two
distinct codes producing identical rendered text would be indistinguishable here.
The 413 distribution [O6] does not suffer this limitation — it was recovered from
`assistant/attempt` stream failures, which do carry `failure.code` and
`failure.status`.

**8.3 Unobservable provider behaviour.** Whether the provider sent a body the
adapter discarded, or genuinely sent an empty body, is not distinguishable from
the persisted log alone [O7]. Either way, the synthesized fallback string is what
reaches the classifier, so Mechanism A is unaffected. The byte-versus-token
finding in [README §5](README.md) is marked `[inferred]` for this reason: the
byte threshold is provider-side and unpublished, and the alternative explanation
— a genuinely malformed request — is not excluded by the available evidence.

**8.4 Snapshot-selection sensitivity.** Because snapshots overlap and are not
nested, the reported totals depend on which file is selected per session [O3].
Both forms are reported for every figure. Selecting by event count alone was
tested and **silently dropped recent evidence** — one directory reported 5
compactions instead of 7, and 413 failures disappeared entirely — so the tool
scores by recency first, volume second.

**8.5 Static prior-art analysis, with one exception.** Compatibility and coverage
claims in [PRIOR-ART.md](PRIOR-ART.md) are mostly source-level reading rather than
execution, and the single boot-failure citation is quoted from a third party's own
record [P6], not reproduced here. Eight of the twenty repositories were assessed
from metadata only and are marked as such.

**The exception is [P1]**, whose version gate was a stated risk and is now a
measured result [O15][O16]: it installs, loads, and reclassifies correctly on a
`0.2.0-rc.2` host, with one caveat reported in
[PRIOR-ART §5.2](PRIOR-ART.md). That measurement covers **one plugin on one host
version**; it does not generalise to the other nineteen repositories, and it does
not cover `0.2.1-alpha.1`.

**8.6 One unresolved conflict in a prior-art source.** `huohua-dev`'s README
states defaults (`thresholdRatio: 0.9`, `outputReserveCap: 0`) that disagree with
its source `DEFAULTS` (`0.85`, `20000`) [P4]. Both were read; neither could be
confirmed as current. Its numeric defaults are therefore treated as unverified.

**8.7 The image-rejection caveat is inferred, not measured.** [O16] establishes
that the plugin reclassifies any `status === 413` regardless of wording. Whether
the provider actually returns image-size rejections as 413 **on this route was not
measured**; the practical exposure therefore depends on an unverified premise.
Every observed 413 in this corpus was a whole-request size refusal [O6], but the
corpus contains no image-rejection 413 to serve as a counterexample.

**8.8 Recommendations are verified on one host version only.** Every
configuration block published in [`config/`](config/README.md) was constructed
against `0.2.0-rc.2` [O20], and seven malformed variants were confirmed rejected
[O21]. **`0.2.1-alpha.1` was not tested.** The engine's validation path is
unchanged between the two revisions as far as the cited source shows [S0a][S0b],
but that is an inference from source, not a measurement.

**8.9 A test can pass through the wrong gate.** Two verification attempts in this
study were initially wrong in the same way — they called a low-level helper and
reported its behaviour as the system's behaviour:

- The plugin's reverse-case test first called `oversizeFailure()` directly,
  bypassing the guards in `classifyOversizeFailure()`, and appeared to
  reclassify all eight negatives [PRIOR-ART §7](PRIOR-ART.md).
- The configuration test first called `BasicCompactionEngine.Config()`, which
  runs only the schema layer; three malformed blocks appeared to be accepted
  [O19].

Both were corrected by entering through the real path. **Testing a guard means
entering through the gate, not around it** — and the corrected runs are the ones
reported here.
