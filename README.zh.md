# dsh-compaction-guide

**DeepSeek Harness 自动压缩指南：长会话为什么会坏、哪些已经被修好、哪些无法修。**

> **这是一份指南，不是一个软件包。** 没有东西需要安装。仓库的主体是文档；
> 诊断工具与验证脚本的存在是为了让每一项主张都可核查，而不是作为产品。
>
> **引用约定。** 事实性陈述带行内标记 —— `[S…]` 固定版本源码，`[O…]` 本研究的测量，
> `[P…]` 先行工作 —— 全部解析于 [`REFERENCES.md`](REFERENCES.md)。**推断而非实测**
> 的结论标 `[inferred]`。以两种口径给出的数字分别标注 *去重* 与 *合并* [O3]。

## 摘要

DeepSeek Harness 0.2.0-rc.2 的自动压缩，在一个长期运行的会话语料上**多数时候失败**：
**51 次启动、9 次成功（17.6%）** [O4]。失败并非分散于多种原因 ——
**约 95% 携带同一条错误文本** `pi-ai detected context overflow for model "…"` [O5]。

识别出三条相互独立的机制，各自用对照实验隔离：

1. **请求分类缺陷使溢出恢复不可达。** 响应体不含提供方消息的 HTTP 413 被归类为
   `INVALID_REQUEST`，而恢复钩子要求 `CONTEXT_WINDOW_EXCEEDED` [S1][S3][S4]。
   观测到的 239 次 413 中，**100%** 被误判 [O6]。
2. **摘要请求无界。** 它逐字重放被压缩区 [S6]，而溢出路径通过传入零保留预算
   把该区域放到最大 [S5][S9]。在只改变窗口大小的对照中：
   **1,000,000 token 下 7/7 成功，262,144 下 1/22** [O8]。
3. **没有退避、没有熔断、没有用户可见信号。** 单个回合内记录到 18 次连续失败，
   且**重试间隔不随失败次数增长** [O11][S11]。

对 20 个仓库的先行工作调研发现：机制 1 **已被一个维护中的插件解决** [P1] ——
已在本机验证可用 [O15] —— 机制 2 **被另外两个从结构上消除** [P2][P5]。
机制 3 **没有任何实现，且不可能有**：可行性测试表明没有任何扩展点能抑制一次压缩尝试 [O24]。

**因此本指南记录、验证、并指向已有的修复，而不是再发布一个竞争品。**

## 1. 测量基础

全部计数来自 **137 个会话目录下的 158 个日志文件** [O1]，用 Node 原生 zstd 逐帧解码。

三个方法学陷阱被记录，因为每一个都会实质改变数字：

**1.1 整块 zstd 解码会静默地只返回第一帧。** 在某个日志上，整块
`zstdDecompressSync` 返回 **188 字节**，而逐帧解码返回 **25,048,287 字节 /
709 帧（7,455 事件）**，且**不抛异常** [O2]。

**1.2 会话快照互相重叠，全部计入会抬高每一个总数。** 一个会话目录保留
`session.jsonl.zstd`、`session.v3.jsonl.zstd`、`session.v4.jsonl.zstd` ——
它们是**同一会话的累积视图**，不是互不重叠的分段 [O3]。每个数字都给出两种口径：

| 量 | 去重 | 合并快照 |
|---|---|---|
| `compaction/start` | **51** | 84 |
| `compaction/summary`（成功） | **9** | 21 |
| 失败闭合 | **42** | 63 |
| 成功率 | **17.6%** | 25.0% |
| `413 → INVALID_REQUEST` | **239** | 478 |

去重列是用户实际体验到的比率；合并列把一个会话按其存储快照数重复计入。

**1.3 按子串计数会产生假阳性。** 早期一遍用搜索 `CONTEXT_WINDOW_EXCEEDED`
得到 248 次「溢出命中」。其中一个**仅仅讨论过**该常量的会话贡献了 66 次，
而**真实错误事件为零** [O13]。这就是诊断工具按结构化事件类型与载荷字段计数的原因。

第四个限制涉及分类而非计数：**`compaction/end` 不持久化错误码** ——
它把 `error` 存为 `errorChain()` 展平后的字符串，`code`/`name`/`cause` 均缺失 [O14]。
错误码分布因此改为从 `assistant/attempt` 流式失败中恢复。

## 2. 机制 A —— 溢出恢复不可达

### 2.1 分类路径

适配器按此顺序分类失败的请求 [S1]：

```ts
else if (isContextWindowExceededError(detail)) code = 'CONTEXT_WINDOW_EXCEEDED'
else if (status === 400 || status === 413 || type === 'invalid_request_error') code = 'INVALID_REQUEST'
```

**顺序是正确的**：文本判定先于状态码判定。缺陷在其上游 —— 当响应体不含
`error.message` 时，适配器合成一条兜底串 [S2]：

```
DeepSeek Messages request failed (413)
```

该串未指涉任何上下文边界，于是三条正则全部落空 [S3]，错误落到 `status === 413` 分支。

恢复钩子恰好由**未被赋予**的那个码把关 [S4]：

```ts
if (failure.code !== CONTEXT_WINDOW_EXCEEDED_CODE) return next()
```

**适配器自己的兜底消息，击败了它所喂给的分类器。**

### 2.2 证据

**分布。** 观测到的 239 次 413 中，**239 次（100%）** 被判为 `INVALID_REQUEST`，
零例外 [O6]。每个抽样到的 413 都携带同一条兜底文本，且**没有一个携带
提供方撰写的 `error.message`** [O7]。

**对照实验。** 在同一会话内，同一模型、同一声明窗口，唯一变量是 HTTP 状态 [O10]：

| 状态 | 赋予的码 | 是否触发压缩 | 结果 |
|---|---|---|---|
| **400** | `CONTEXT_WINDOW_EXCEEDED` | **3 次**，分别在 +9ms / +25ms / +32ms | **全部成功** |
| **413** | `INVALID_REQUEST` | **从未** | 失败 |

这排除了「压缩逻辑本身坏了」：只要逻辑被触达，它就成功。

### 2.3 后果

`INVALID_REQUEST` 也不在可重试码集内 [S12]。观测到的序列是：请求被拒 →
压缩从未被调用 → 上下文从未被回收 → 会话无法推进。

用户可见的**交接**状态**不是**由压缩失败导致的 [O12]。被交接的会话在交接当下
`failedEnds = 0` 且压缩次数为零；链条是：请求失败 → 无压缩 → 卡死 →
**用户运行 `/rescue`** → 交接。

**怎么办**：[`guide/quick-guide.md` §3](guide/quick-guide.md)。

## 3. 机制 B —— 摘要请求把自己撑爆

### 3.1 三行相互作用

**无界输入。** 摘要器构建一个请求，逐字包含整个被遮蔽区域，无分块、无体积守卫 [S6]。

**最大化区域。** 溢出路径传入字面量 `0` 作为保留预算 [S5]。保留区选择从尾部累积
节点直到预算满足 [S9]；预算为 `0` 时第一次迭代即满足条件，于是保留的尾部只剩
单个节点，被压缩区扩张到几乎整个 surface。

**未固定的目标。** 摘要模型解析为 `configured ?? latest ?? agentTarget` [S7]，
其中 `latest` 是会话**当前路由到的模型**。

三者合起来：**最大可能的输入，被送给最小可用的窗口，且恰在该窗口已经满了的时候。**

### 3.2 证据

**对照实验，窗口大小为唯一变量** [O8]：

| 摘要路由窗口 | 压缩次数 | 成功 | 失败 |
|---|---|---|---|
| 1,000,000 | 7 | **7** | 0 |
| 262,144 | 22 | 1 | **21** |

**物理记录。** 失败会话中那唯一一次成功压缩携带 `shadowedTokenCount = 557,896`
与 `inputTokens = 791,091` [O9] —— **557K token 的历史被送进 262K 窗口。**

### 3.3 为何无法自愈

摘要调用是**直连**的 `ctx.llm.stream()` [S8]，不经过 agent loop。
唯一的溢出恢复入口是 `agent/request-error` waterfall，由 loop 派发。
直连调用因此**永不派发该事件**，于是**摘要溢出没有任何恢复路径**。

**怎么办**：[`config/README.md`](config/README.md) —— 包括设置**放在哪里**，
那不是大多数人会去找的地方 [O17][O18]。

## 4. 机制 C —— 无退避、无熔断、无信号

`agent/pre-step` 监听器捕获每一次压缩失败并记录 [S11]：

```ts
ctx.logger.warn(`step compaction failed: ${message}; continuing the turn`)
```

回合继续，上下文依旧满，下一步再次触发压缩。`maxOverflowRetries` 只在
`agent/request-error` 路径计数；`pressure` 路径没有会话级计数器 [S14]。

**实测节奏** [O11]：

| 量 | 值 |
|---|---|
| 单回合内连续失败 | **18** |
| 最小间隔 | 76,631 ms |
| 中位间隔 | 101,173 ms |
| 最大间隔 | 778,069 ms |
| 失败总跨度 | 5,391 秒（89.9 分钟） |

退避会表现为间隔递增。观测到的分布是平的：**间隔不随失败次数增长** [O11]。

### 4.1 这一条无法用插件修复

熔断行为要求**在一次尝试发生之前跳过它**。所有扩展点都被枚举过，没有一个能做到 [O24]：

| 扩展点 | 为何无法阻断 |
|---|---|
| `agent/pre-step` | 调用发生在 `compaction-basic` **自己的监听器体内** [S14]，不在 `next()` 之后 —— 抢排序无用 |
| `compaction/summary-error` | 只在失败**之后**触发，管不了下一次 |
| `llm/stream` | 包裹调用，但无法决定「不调用」 |
| `session/event` | 只读观测 |
| surface 改写 | 治的是「少触发」，不是「失败了别重试」 |

所需改动是**上游监听器内部**的一个 guard：

```ts
// 仅上游可改 —— 任何插件都无法插入
if (breakerTripped(session)) return next()
```

**这个否定性结论被完整公开**，因为该布局无法从任何单一扩展点看出，插件作者
完全可能先投入精力才发现。证据见 [`verify-feasibility/`](verify-feasibility/)。

**今天你能做的**：减少触发次数（[`guide/quick-guide.md` §7](guide/quick-guide.md)），
以及上报上游。

## 5. 字节与 token 的错配

触发阈值由 token 计算 [S10]：

```
threshold = floor(min(W × thresholdRatio, W − O − headroomTokens))
```

对声明 `contextWindow: 1000000, maxTokens: 256000` 的路由，得到
`min(800000, 1000000 − 256000 − 65536) = 678,464` token。token 预算因此报告有余量，
而该尺寸下序列化后的请求已是数兆字节。

执行**字节**限制的传输层或代理，在这套计算中无处被计价。

**`[inferred]`** 「字节限制拒绝即观测到的 413 成因」这一推断，与状态码、空响应体 [O7]
及上述算术一致，但 harness 无法观测提供方的字节阈值，确切上限未公开。
另一种解释**未能排除**。这一区分不影响机制 A 与 B（两者均由直接测量确立 [O8][O10]）。

## 8. 对有效性的威胁

**单语料范围。** 全部计数来自单一用户的会话日志 [O1]。**频率** ——
17.6%、239/239、18 次连续 —— 描述该语料，**不外推**。

**持久化层限制。** `compaction/end` 省略错误码 [O14]。

**提供方行为不可观测。** §5 中的字节阈值为提供方侧且未公开；该结论标 `[inferred]`。

**快照选择敏感性。** 总数取决于每会话选取哪个快照 [O3]；两种口径均已给出。

**先行工作为静态分析。** **有一处例外** —— [P1] 已在真实宿主上安装并驱动 [O15]。
20 个仓库中有 8 个仅基于元数据评估。

**推荐仅在单一宿主版本上验证。** 全部配置结论针对 `0.2.0-rc.2`
[O20][O21][O22]。**`0.2.1-alpha.1` 未测试。**

**没有任何端到端验证。** 本仓库中没有任何测量表明：把推荐配置应用到当前失败的会话上
会使其成功。机制已理解、效应方向已确立 [O8]，但读者应用它们是在做
**有依据的改动，而非已验证的修复**。

**测试可能从错误的门通过。** 本研究中三次验证尝试最初都以同样的方式出错 ——
它们驱动了低层 helper 或不完整的测试台，并把其行为当作系统的行为上报。
每一次都通过走真实路径得到纠正；上报的是纠正后的结果，失败尝试保留在
`verify-*/` 作为证据 [O19][O26]。

## 9. 复现本指南

**每一项主张都注明了产出它的脚本。** 有的读上游源码，有的需要安装 harness 包，
有的什么都不需要 —— 完整分类（含预期输出与失败症状）见
[`REPRODUCING.md`](REPRODUCING.md)。

两个无需任何前置条件的：

```sh
# 去重计数 —— 面向用户的比率
node tools/doctor.mjs "$DSH_HOME/sessions"

# 合并全部快照 —— 复现 §1.2 中偏高的总数
node tools/doctor.mjs "$DSH_HOME/sessions" --merge

# 机器可读
node tools/doctor.mjs "$DSH_HOME/sessions" --json

# 隐私门禁
node tools/privacy-check.mjs .
```

其余：

```sh
pnpm install                              # 将 harness 锁定到 0.2.0-rc.2
pnpm verify:config                        # 配置正确性
pnpm verify:risk                          # 残余风险
pnpm verify:reachability                  # 服务可达性

git clone https://github.com/deepseek-ai/deepseek-harness.git /tmp/dsh
git -C /tmp/dsh checkout 5badb150         # 锁定引用所用的提交
node verify-refs/check-refs.mjs /tmp/dsh  # 解析每一条 [S…] 引用
```

源码声明可通过检出固定提交 [S0a][S0b] 并阅读所引行号验证。行号由
[`verify-refs/check-refs.mjs`](verify-refs/check-refs.mjs) 解析 ——
**版本变更后请重跑它**；解析失败说明引用与所检出的版本不再匹配，而不是脚本坏了。

> **可复现性状态。** 本仓库全部 20 个脚本，都在发布前针对固定依赖端到端跑过，
> 语料数字（51 / 9 / 42 / 239）已确认可复现。按 [`REPRODUCING.md`](REPRODUCING.md)
> 操作的读者应看到相同输出。**若有任何一项无法复现，那是值得上报的缺陷** ——
> 本研究中三次验证尝试第一次都是错的，这里发布的是修正后的版本。
